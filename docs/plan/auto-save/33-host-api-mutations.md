# Scope

Audit of the host web’s settings/account/drawer query and mutation contracts, including the browser client, React Query invalidation, autosave/optimistic behavior, daemon route semantics, and the same-origin BFF. Sources inspected were `web/`, `src/api/`, `src/store/`, and focused tests. Registry-plugin implementation is out of scope.

**Overall finding:** the host has a good shared autosave primitive and generally safe validation, but its mutation protocol is last-write-wins rather than CAS. `PUT /config` is semantically a partial patch despite its verb, while several nested arrays/maps are full replacements. The client protects edits within one autosave controller, not across independent controllers or browser tabs. There is no `If-Match`, ETag precondition, revision, or version field on settings mutations.

# Missing or inconsistent auto-save

- **No optimistic concurrency contract.** The mutable settings responses contain canonical data but no revision/version, and no route checks `If-Match` or an equivalent expected version. The BFF has no conditional-write handling (`web/app/api/[...path]/route.ts:17-58`; `web/lib/proxy.ts:123-147`). Last successful write wins across tabs/devices.
- **Shared `ConfigStore` writes can lose independent edits.** `ConfigStore.update()` reads then writes without a transaction (`src/store/configStore.ts:1178-1187,1212-1278`). The settings page runs independent autosave controllers for defaults, model windows, model lists, auto-update, and push contact (`web/app/settings/page.tsx:275-292`). `useAutoSaveStatus` serializes only one controller’s queue (`web/lib/useAutoSaveStatus.ts:45-67`), so two requests can read the same old config and overwrite each other’s merged result.
- **Whole-snapshot fields are vulnerable to stale drafts.** `brain.providers`, context-window maps, hidden OAuth lists, tool-deferral maps, model notes, and permission rule maps intentionally replace wholesale (`src/store/configStore.ts:1221-1234,1247-1251`; `src/store/userSettingStore.ts:188-190,294-301`). This is safe only when the caller owns a current snapshot; there is no server-side stale-snapshot rejection.
- **Permission rules are not race-safe.** `PermissionRulesCard` immediately displays a local optimistic replacement, but calls `save.mutate()` without serialization (`web/modules/account/PermissionRulesCard.tsx:96-109`). Rapid edits can arrive out of order, and a successful query invalidation re-seeds local rules on every `permissions.data` change (`web/modules/account/PermissionRulesCard.tsx:83-88`), potentially replacing an in-progress local edit with an older refetch.
- **Canonical mutation responses are inconsistently consumed.** Most hooks invalidate and ignore the returned canonical object (`web/lib/mutations.ts:82-93,298-304,508-546`). This causes an avoidable refetch and leaves the local form responsible for interpreting clamps/server normalization. Navigation and project-file writes demonstrate the stronger pattern of writing the accepted response/value into cache immediately (`web/lib/mutations.ts:94-105,364-373`).
- **Error presentation is inconsistent.** The transport has a useful `ElowenApiError` with status, short `error` code, and parsed `details` (`web/lib/elowenClient.ts:9-24,31-37`), and daemon validation consistently emits `{ error }` (`src/api/server.ts:49-59`). However, settings frequently toast `String(error)` instead of `apiErrorMessage(error)` (`web/app/settings/page.tsx:245-247,277-283`; `web/modules/account/CliSection.tsx:98-128`), while direct drawer fetches collapse failures to generic strings (`web/modules/settings/ToolDeferralModal.tsx:88-101,146-161`). 409 conflicts and field-level validation therefore do not have one user-facing path.
- **Direct fetch bypasses the typed client contract.** `ToolDeferralModal` reads `/api/config/tool-deferral` with raw `fetch` and does not parse `ElowenApiError` (`web/modules/settings/ToolDeferralModal.tsx:88-101`). This is a read-only catalog, but it makes error shape and retry behavior different from all typed settings queries.
- **Mutation invalidation is narrower than shared ownership in a few places.** Config saves invalidate `['config']`, while settings that derive catalogs or dependent views must add their own invalidation. Brain provider saves do this explicitly (`web/lib/mutations.ts:298-304`), dashboard saves invalidate both config and recap (`web/modules/settings/DashboardSection.tsx:66-76`), but generic config callers can still forget derived keys because the contract is not centralized.
- **Autosave status is controller-local, not request-generation-aware across hooks.** The shared hook protects its own queued saves and unmount flush (`web/lib/useAutoSaveStatus.ts:7-17,45-67,85-105`), but it cannot order two independent hooks targeting the same resource. “Saved” therefore means that one request succeeded, not that the latest global snapshot is durably the one shown.
- **Successful writes can be followed by asynchronous runtime activation.** Plugin config explicitly models this with HTTP 202 and `pending` (`src/api/routes/plugins/index.ts:116-137,500-518`; `web/lib/usePluginConfigDraft.ts:21-24,99-101`). Core config and CLI settings also launch background brain re-application (`src/api/routes/config.ts:301-307`; `src/api/routes/auth.ts:214-240`) but return no equivalent activation status, so “saved” can mean persisted while runtime convergence is still pending.

# Legitimate exceptions

- Password changes require current-password verification and must not be triggered by typing (`src/api/routes/auth.ts:78-89`).
- Avatar upload is a file/side-effect operation, not a field patch (`src/api/routes/auth.ts:284-301`).
- OAuth connect/input, push subscription, restart/update, log deletion, plugin deletion/data clearing, and similar actions are explicit because they involve consent, external verification, destructive effects, or lifecycle control.
- Brain provider editing is credential-bearing and list-atomic; preserving masked secrets while replacing the provider list is a valid explicit-save boundary (`web/modules/settings/BrainProvidersSection.tsx:450-484`; `src/store/configStore.ts:1221-1227`).
- Tool-loading policy is a multi-control policy editor where committing one coherent snapshot is preferable to firing a request per slider/toggle (`web/modules/settings/ToolDeferralModal.tsx:146-161,247-251`).
- Plugin role removal uses confirmation and immediate commit because it is a destructive row operation (`web/modules/settings/PluginConfigEditor.tsx:337-362,810-816`).

# Reusable existing pattern

1. Seed local state exactly once from the query; do not re-seed on invalidation while an edit is pending (`web/modules/account/CliSection.tsx:43-58`; `web/app/settings/page.tsx:221-237`).
2. Use `useAutoSaveStatus` for bounded debounce, serialized follow-up saves, close/unmount flush, visible `saving/saved/error`, and retry (`web/lib/useAutoSaveStatus.ts:7-17,45-105`).
3. Send the smallest field patch for independently owned scalar fields; send a complete snapshot only when the field’s semantics are ordered/set-like or the UI intentionally owns the whole object.
4. Consume the accepted server response for cache state when it is the canonical full object, as navigation does (`web/lib/mutations.ts:94-105`), and invalidate dependent queries separately when derived catalogs/views change.
5. For optimistic UI, snapshot and restore the exact affected cache entries, then invalidate on settle; plugin toggling is the clearest example (`web/lib/mutations.ts:130-159`).
6. Preserve plugin-specific snapshot/secret rules in one shared helper (`src/api/routes/plugins/index.ts:62-86`; `web/lib/usePluginConfigDraft.ts:37-112`).

# Recommended migration notes

- Define one versioned resource contract for settings blobs: return a monotonic `version` (or ETag), accept `expectedVersion`/`If-Match`, and return a structured 409 containing current canonical data plus the conflicting version. Do not silently merge stale full snapshots.
- Make `ConfigStore.update()` atomic around read/merge/write, or move to SQL-level compare-and-swap. A transaction alone prevents interleaving but does not reject stale browser snapshots; use both where full replacements exist.
- Keep partial scalar patches, but explicitly document full-replacement members in types and route schemas. Prefer resource-specific endpoints for high-risk whole maps/lists if independent editing is expected.
- Centralize mutation creation/invalidation for config-derived settings so every write updates the canonical cache and dependent catalogs consistently. Prefer `setQueryData` from the accepted response before invalidation where the response is complete.
- Serialize writes by resource key across all hooks/components, not only inside one `useAutoSaveStatus` instance. This is required for multiple settings pods sharing `/config`, CLI settings, or permissions.
- Route all settings errors through `ElowenApiError`/`apiErrorMessage`; preserve status and structured details for conflict/validation UI. Replace direct raw `fetch` in settings drawers with the typed client or a shared query helper.
- Preserve explicit Save for credentials, destructive/multi-step atomic actions, consent, and external verification; do not convert those mechanically to per-keystroke autosave.
