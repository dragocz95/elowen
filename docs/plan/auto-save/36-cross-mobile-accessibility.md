# Scope

Audit of host and registry-plugin settings/forms that open as mobile fullscreen dialogs, desktop drawers, or fullscreen workspaces. Focus: auto-save status announcements, focus placement/return, disabled controls, keyboard operation, and close/Escape behavior while persistence is pending. Sources inspected: `/var/www/elowen/web` and `/var/www/elowen-plugins/plugins` plus focused tests.

# Missing or inconsistent auto-save

- **Pending close is not consistently owned.** `Modal` always leaves its header close control active (`/var/www/elowen/web/components/ui/shadcn/dialog.tsx:214-225`), and Radix Escape calls the surface `onClose`. Auto-save editors call `flush()` and immediately unmount (`ContextWindowModal.tsx:30-31`, `ModelNoteModal.tsx:24-25`); `flush()` returns `void`, so it cannot wait for the network request. The hook explicitly allows an in-flight request to finish after unmount (`useAutoSaveStatus.ts:40-43,90-105`; regression test `web/tests/lib/useAutoSaveStatus.test.tsx:41-57`). This protects durability but leaves no visible status, cancellation choice, or confirmation while the request is still pending.
- **The most important autosave status is often behind the modal.** Brain/runtime/retention status is aggregated into the settings hero (`BrainRuntimeSection.tsx:143-156`, `app/settings/page.tsx:472-480`), but the modal is a body-level isolated dialog. The page hero is inert/`aria-hidden` while open (`overlayStack.ts:48-56`), so a screen-reader user editing sliders cannot hear Saving/Saved/Error or reach Retry. Compact thresholds and cron jobs have the same structural issue when their status lives on the row behind an open detail rail; cron's row comment confirms the status is deliberately rendered outside the drawer (`JobsSettings.tsx:447-450`).
- **Autosave status is missing from several editing surfaces.** Brain limits, runtime limits, retention, and compact thresholds expose no `AutoSaveStatus` or Retry in the active drawer/modal. A successful slider change is visually reflected in the value, but a failed request is only available through the parent toast/hero path, which is inaccessible behind the modal during the edit.
- **Close controls are not disabled while autosave is pending.** Done/close remains enabled in ContextWindow, ModelNote, Personality, and modal slider editors. This is not data loss because the hook flushes, but it is ambiguous: the user cannot tell whether closing waits, whether the save succeeded, or where to retry. The explicit-save ToolDeferral and MCP editors have the same issue for a different reason: their Save button is disabled while busy, but the header close and Cancel paths remain available (`ToolDeferralModal.tsx:248-251`; `McpServersPage.tsx:294-303`).
- **Status semantics differ by surface.** `AutoSaveStatus` uses `role="status" aria-live="polite"` for Saving/Saved and `role="alert"` for failure (`web/components/ui/AutoSaveStatus.tsx:7-26`). Plugin immediate actions use `aria-live="polite"` only while pending and do not announce completion (`TeamsWorkspace.tsx:254-255`). Editor writes rely on toast announcements and a visual/labelled unsaved dot (`editor/StatusBar.tsx:29-44`) rather than a persistent saving/saved state.
- **Disabled-state explanations are not uniform.** Native `disabled` correctly removes controls from keyboard interaction, and the shared focus cycle recomputes disabled controls (`web/components/ui/focusCycle.ts:10-23`). However, disabled Save/Run/Connect controls generally have no adjacent explanation or `aria-describedby`; the reason must be inferred from nearby draft state. The disabled locked-tool button in `ToolDeferralModal.tsx:231-237` is better because its accessible name includes the reason.
- **Keyboard coverage is strongest in the shared shell, weaker at lifecycle boundaries.** Modal focus trapping, Escape ownership, nested overlay ordering, and focus return are covered by Radix and host tests. Slider, segmented, and editor shortcuts are covered in focused tests. There is no equivalent regression coverage for Tab/Escape/close while a save is pending, especially on a phone fullscreen presentation.

# Legitimate exceptions

- **MCP server configuration** contains connection credentials/environment and changes several fields that must be committed as one coherent server record. Explicit Save is justified, but pending Save should own all dismissal paths until the request settles or provide an explicit “leave while saving” decision.
- **Tool-deferral policy** is a multi-step catalog editor whose local changes are intentionally reviewed as one atomic runtime patch. Explicit Save/Cancel is justified. Its current Save lock is appropriate; its close/cancel behavior during the request is not fully guarded.
- **Editor writes** are explicit, externally meaningful file mutations, and uploads, rename/delete, and commit-oriented workflows should not be silently persisted on every keystroke. The mobile takeover's labelled Back/Escape contract is appropriate. Save success/failure via accessible toast is a reasonable exception to a persistent autosave indicator.
- **OneDrive Connect** creates an external mirror/connection and must remain explicit. Its selected-folder validation and pending button lock are appropriate.
- **Confirmation dialogs** are the reusable correct model for irreversible async actions: `ConfirmDialog` blocks header close, Cancel, and Escape while pending, sets `aria-busy`, and keeps focus owned by the dialog (`web/components/ui/ConfirmDialog.tsx:24-35,72-77,120-157`).

# Reusable existing pattern

- Use `Modal`/`WorkspaceDetailRail`/`WorkspaceTakeover` for all mobile and fullscreen surfaces. They already provide `role="dialog"`, `aria-modal`, labelled headings, Radix focus trap, Escape routing, body isolation, safe-area/dvh geometry, and focus restoration.
- Use `useAutoSaveStatus` for debouncing, validity gating, serialized follow-up writes, stale-response protection, retry, and teardown flush (`web/lib/useAutoSaveStatus.ts:6-24`).
- Render `AutoSaveStatus` **inside the active modal/drawer**, not only in the row or page behind it. Keep a Retry control in the same focus scope as the failed edit.
- For a close action that must wait, follow `ManageSelectionModal`'s async-save ownership: await the persistence promise and close only after success; on failure keep the modal open and retryable (`web/components/ui/ManageSelectionModal.tsx:189-200`). For irreversible work, use `ConfirmDialog`'s pending dismissal block.
- Preserve the stronger data-flow patterns already present: plugin config draft does not reseed over newer edits and serializes full-snapshot writes (`web/lib/usePluginConfigDraft.ts:37-80`); cron jobs protect deletion against an in-flight save (`JobsSettings.tsx:288-321,354-363`); the editor retires only the exact content that was sent (`ProjectEditor.tsx:183-204`).

- Autosave controller behavior is covered for debounce, status transitions, retry, unmount flush, in-flight completion after unmount, Activity hide/show, and stale responses in `/var/www/elowen/web/tests/lib/useAutoSaveStatus.test.tsx:6-102`.
- Slider semantics and keyboard changes are covered for host Brain/Runtime limits in `/var/www/elowen/web/tests/modules/settings/BrainLimitsModal.test.tsx:33-75` and `/var/www/elowen/web/tests/modules/settings/RuntimeLimitsModal.test.tsx:25-85`; compact-threshold keyboard/reset behavior is covered in `/var/www/elowen/web/tests/modules/account/CompactThresholdsDrawer.test.tsx:24-40`.
- Cron autosave and keyboard builder behavior are covered in `/var/www/elowen-plugins/tests/cronjob-ui.test.tsx:321-386,442-466`; MCP pending reconnect/disabled-control behavior is covered in `/var/www/elowen-plugins/tests/mcp-ui.test.tsx:43-70,78-158`; editor write race handling is covered in `/var/www/elowen-plugins/tests/editor-ui.test.tsx:328-396`.
- Gaps: no focused test asserts that a phone fullscreen editor keeps the modal open or communicates state while autosave is pending; no test covers close-button or Escape during an in-flight autosave; no accessibility test verifies that Saving/Saved/Error remains in the active dialog's accessibility tree; no test verifies Retry from inside Brain/runtime/retention or compact-threshold drawers; no plugin test covers MCP/Tool-deferral close or Escape while the explicit mutation is pending.
- Runtime/mobile verification should include a real narrow viewport with a screen reader or accessibility tree inspection: open each drawer/modal, change a field, press Escape/close immediately, verify focus return, verify the save completes without stale overwrite, and verify failure leaves an actionable Retry in the active surface.

# Recommended migration notes

- First strengthen the shared autosave contract with an awaitable flush/settle signal (or a close policy that can distinguish “debounced only” from “request in flight”). Do not rely on fire-and-forget teardown as the only user-facing guarantee.
- Make active editing surfaces expose one local status region and Retry control. If a parent also shows aggregate status, keep both but ensure the modal/drawer copy is the one available while the background is inert.
- Define one shared pending-dismissal policy: either disable close/Escape until the save settles, or allow leaving only after an explicit “save continues in background” choice. The safest default for settings is to wait; preserve `ConfirmDialog`'s blocking behavior for destructive actions.
- Add regression tests for pending close/Escape, focus return after delayed success/failure, live-region presence inside fullscreen dialogs, and keyboard traversal with disabled controls. Prioritize Brain/runtime/retention, compact thresholds, cron jobs, and the explicit-save MCP/Tool-deferral drawers.
