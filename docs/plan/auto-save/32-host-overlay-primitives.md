# Host overlay primitives auto-save audit

## Scope

Audited the shared host overlay and form primitives in `/var/www/elowen/web`: `Modal`, `WorkspaceDetailRail`, `ConfirmDialog`, `Field`, the Radix-backed dialog/alert-dialog wrappers, `overlayStack`, `WorkspaceTakeover`, and the shared autosave/status bridge used inside these surfaces. Direct callers were inspected where they determine close, pending, error, retry, or stale-draft behavior. The audit is about one canonical autosave experience: validated edits persist automatically, status is visible, failed writes are retryable, and closing must not silently discard or hide the last edit.

## Missing or inconsistent auto-save

- **`Modal` has no shared close ownership for dirty or pending content.** The header close is wired directly to `onClose` (`Modal.tsx:143-152`), Escape reaches `onClose` through `Dialog` (`:94`), and a backdrop press calls `onClose` (`:108-116`). `ModalFooter` accepts arbitrary status content (`:185-192`) but cannot disable or defer any of those exits. Each autosaved caller must therefore reimplement the policy, and most do not.
- **`ManageSelectionModal` contradicts its own async-safe intent.** Its save function awaits `onSave` before calling `onClose` and catches rejection (`ManageSelectionModal.tsx:189-199`), but `saving` only disables footer buttons (`:297-300`). The enclosing `Modal` still has an active header close, Escape, and backdrop path (`Modal.tsx:94-116`, `:143-152`), so a user can unmount the picker while its mutation is in flight. The existing test only covers rejection after pressing Save (`web/tests/components/ui/ManageSelectionModal.test.tsx:110-116`), not those other dismissal paths.
- **Closing an autosave modal hides the only retry surface.** `ModelNoteModal` flushes and immediately closes (`web/modules/settings/ModelNoteModal.tsx:24-27`); `ContextWindowModal` does the same (`web/modules/settings/ContextWindowModal.tsx:29-33`); Personality closes by toggling `editing` (`web/modules/account/PersonalitySection.tsx:99-115`). `useAutoSaveStatus` intentionally lets an async flush finish after unmount (`web/lib/useAutoSaveStatus.ts:40-43`, `:90-102`), but that means a failed close-time write cannot display `error` or its retry in the unmounted modal. The write is not silently dropped, but the canonical visible error/retry contract is lost.
- **The detail rail has the same close-time gap.** `MemoryDetail` offers status/retry and flushes only for Done (`web/modules/memory/MemoryDetail.tsx:90-93`, `:117-123`). Closing `WorkspaceDetailRail` from the parent simply clears the selection (`web/modules/memory/MemoryView.tsx:491-503`), unmounting the editor while its save may still be pending. The rail is read-only in most uses, but its shared API cannot distinguish a safe inspection close from an active edit.
- **`ContextWindowModal` can report a false success for invalid input.** Its callback returns no write when `valid` is false (`web/modules/settings/ContextWindowModal.tsx:28-31`), but the hook is called without `savable: valid`; the controller therefore treats the no-op callback as a successful save. The hook explicitly defines `savable` as the validity gate and says it must be separate from `ready` (`web/lib/useAutoSaveStatus.ts:19-24`, `:26-31`). Retry has the same problem because `retry()` calls `run()` without checking validity (`:104`).
- **`MemoryDetail` uses `ready` as a changing validity gate.** `ready: !!body.trim()` is passed to the hook (`web/modules/memory/MemoryDetail.tsx:90`), although `ready` is documented as seed completion, not current validity. When a previously valid body is emptied after a debounce was scheduled, the effect cleanup cancels the timer but leaves `pending.current` set; a close flush can run the guarded no-op and end in `saved` without a write. The caller should use a stable seed gate and `savable` for the required body.
- **`ConfirmDialog` is only async-safe when callers return the promise and keep the target open.** Several callers close state before starting a mutation and return `undefined`: provider disconnect/remove (`web/modules/settings/BrainProvidersSection.tsx:688-707`), category deletion (`web/modules/memory/CategoryManager.tsx:237-255`), and delete-all sessions (`web/components/brain/BrainSessionsPanel.tsx:167-177`, `:364-372`). `ConfirmDialog` cannot show pending or retain retry ownership for those callbacks; failures become toasts after the confirmation has disappeared. Other callers demonstrate the correct contract by returning an async function and guarding close (`web/modules/users/UsersView.tsx:297-309`, `web/modules/advisor/ChatHistoryRail.tsx:189-209`).
- **`Field` handles validation errors, not persistence errors.** Its `error` is correctly announced and connected to the control (`Field.tsx:82-89`, `:129-134`), but there is no convention for an async save error or retry action. Callers must pair it with `AutoSaveStatus` or independently map server errors into `error`; the primitive cannot make an autosave-compatible form by itself.
- **Overlay focus behavior is strong but not a save policy.** `overlayStack` captures/restores focus and isolates lower layers (`overlayStack.ts:95-129`, `:141-172`), and the Radix tests cover nesting, focus, backdrop, and isolation (`web/tests/components/ui/Modal.test.tsx:132-151`, `:221-341`). None of those paths asserts that a pending save blocks close, that an error remains retryable after a close attempt, or that a stale draft is protected while the overlay is dismissed.

## Legitimate exceptions

- Destructive confirmations should remain explicit and outside-click resistant. `ConfirmDialog` is the right primitive: it does not dismiss on backdrop, starts focus on Cancel, and locks every dismissal path while a promise is pending (`web/components/ui/ConfirmDialog.tsx:24-36`, `:120-155`).
- Passwords and API keys should not be auto-saved. User creation keeps username/password behind Create (`web/modules/users/UsersView.tsx:268-285`), and provider configuration includes a password input/API key and endpoint probing (`web/modules/settings/BrainProvidersSection.tsx:243-275`). Persisting secret keystrokes automatically would increase exposure and would not provide an atomic validation boundary.
- Multi-field CRUD forms and batch selections may keep explicit Save/Create/Select because the operation is a deliberate, grouped commit: project create/edit (`web/modules/projects/ProjectsView.tsx:391-472`), category create/edit (`web/modules/memory/CategoryManager.tsx:128-225`), and selection batches (`web/components/ui/ManageSelectionModal.tsx:135-139`). The exception is the explicit commit, not permission to dismiss while the commit is pending.
- Directory browsing, OAuth connection, diagnostics/capture consent, uploads, and other action-oriented overlays are not ordinary preference edits. Their explicit action or Cancel/Back behavior is appropriate; they still need a pending lock when the action itself is asynchronous.
- Most `WorkspaceDetailRail` instances are read-only record inspection (`web/components/ui/WorkspacePrimitives.tsx:65-88`, `web/modules/projects/ProjectsView.tsx:326-384`, `web/modules/users/UsersView.tsx:261-262`). They are N/A for autosave until an editable child is mounted; `MemoryDetail` is the current counterexample.

## Reusable existing pattern

- `useAutoSaveStatus` is the canonical controller: it consumes the initial seed without writing, debounces validated changes, serializes follow-up writes, flushes on close/unmount, exposes retry, and suppresses state updates after unmount (`web/lib/useAutoSaveStatus.ts:6-24`, `:45-105`). Callers should pass `ready` only for server seeding and `savable` for live validation.
- `AutoSaveStatus` is the canonical visible status: polite Saving/Saved announcements and an alert with Retry on failure (`web/components/ui/AutoSaveStatus.tsx:7-29`). `ModalFooter` already has a status slot (`web/components/ui/Modal.tsx:185-192`), so no second indicator is needed.
- Account profile and platform links show the strongest caller-level pattern: compute only changed fields, seed before enabling writes, pass `savable` separately, and fold multiple statuses with `combineSaveFeedback` (`web/modules/account/AccountView.tsx:171-215`, `:308-325`; `web/lib/saveFeedback.ts:1-13`).
- `usePluginConfigDraft` adds the required stale-draft protections for full-snapshot config: refetches do not overwrite an active draft, writes are serialized, immediate commits flush older debounce work, and the same status/retry/flush contract is returned to the surface (`web/lib/usePluginConfigDraft.ts:37-42`, `:52-112`).
- Async `ConfirmDialog` and the correct `ManageSelection` callers establish the desired mutation shape: return a promise, keep the confirmation mounted, disable dismissal while pending, leave the error visible, and allow a retry (`web/tests/components/ui/ConfirmDialog.test.tsx:107-162`; `web/modules/users/UserDetailPane.tsx:161-193`).

## Tests and gaps

- Shared modal tests cover title/ARIA, presentation, nested z-order, backdrop semantics, Escape, focus entry/return, Tab trapping, inert isolation, phone fullscreen, and nested backdrop ownership (`web/tests/components/ui/Modal.test.tsx:66-108`, `:132-151`, `:221-341`, `:393-426`).
- `ConfirmDialog` tests cover safe initial focus, outside/Escape behavior, async pending lock, duplicate-click protection, rejection display, and StrictMode/Activity lifecycle (`web/tests/components/ui/ConfirmDialog.test.tsx:51-105`, `:107-193`).
- Autosave controller tests cover seed suppression, debounce, saved/error states, retry, unmount flush, in-flight completion, Activity hide/show, and serialized stale-response handling (`web/tests/lib/useAutoSaveStatus.test.tsx:6-102`).
- Field tests cover description/error ARIA wiring, required state, hint accessibility, multi-control fields, and refusal to render unwired ARIA (`web/tests/components/ui/Field.test.tsx:20-190`).
- Missing regression coverage: press header close, Escape, and backdrop while `ManageSelectionModal` is saving; close an autosaved modal or detail rail while its flush is pending; preserve visible retry after a close attempt; invalid `ContextWindowModal` input must not reach `saved`; empty `MemoryDetail` body must not produce a no-op success; and sync `ConfirmDialog` callers must not disappear before their mutation settles.
- No runtime/e2e verification was needed for this read-only audit; the findings are based on shipped source and focused test coverage.

## Recommended migration notes

- Give the shared modal lifecycle one owner. A close request should be able to consult a pending/dirty policy before it reaches header, Escape, or backdrop paths; do not rely on disabling only a footer button. Preserve the existing default for read-only modals.
- Standardize an autosave modal contract around `status`, `retry`, `flush`, and a close policy that either flushes and keeps the surface visible until the write settles or explicitly documents that close may leave the user without retry feedback. `ModalFooter status` remains the visual location.
- Correct autosave call sites to keep `ready` (server seed) separate from `savable` (current validity), especially `ContextWindowModal` and `MemoryDetail`; never represent invalid input as a successful no-op save.
- Require asynchronous confirmation call sites to return their mutation promise and clear the target only after success. Treat a toast-only error after the dialog has vanished as a contract violation unless the action is intentionally fire-and-forget.
- Preserve `Field` as an ARIA/validation primitive rather than teaching it persistence. Pair field-level validation errors with the shared autosave status/retry channel instead of adding a second save protocol to `Field`.
- Add focused tests for the shared dismissal matrix: close button, Escape, backdrop, parent rail close, pending save, rejection, retry, and stale server refresh. This is the smallest regression suite that proves the overlay is safe for autosave rather than merely focus-safe.
