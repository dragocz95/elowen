# Scope

Audit of registry plugin `lsp` at `/var/www/elowen-plugins/plugins/lsp`, its host web/config surfaces in `/var/www/elowen`, the CLI `/lsp` modal, and all persistence APIs used by those surfaces.

The plugin has no plugin-owned browser bundle or `web` manifest section. Its only declared editable setting is the instance-wide boolean `diagnosticsEnabled` in `elowen-plugin.json:44-52`, with the same default/fallback implemented in `src/config.ts:3-22`. Therefore the web UI is the host's generic Settings → Plugins workspace, not an LSP-specific page.

# Missing or inconsistent auto-save

- **Activation-pending state is lost in the ordinary web autosave path.** The backend deliberately distinguishes durable persistence from delayed live activation: `appliedConfig()` returns HTTP 202 with `pending:true` after persistence succeeds but reload is deferred (`/var/www/elowen/src/api/routes/plugins/index.ts:116-137`), and the LSP config route uses that contract (`:500-518`). The client types the response as pending-capable (`/var/www/elowen/web/lib/elowenClient.ts:134-135`), but `usePluginConfigDraft` awaits `queueSave()` without inspecting its response (`/var/www/elowen/web/lib/usePluginConfigDraft.ts:66-80`). The toolbar consequently renders plain “Saved” (`/var/www/elowen/web/components/ui/AutoSaveStatus.tsx:18-21`) even if LSP is still running with the previous generation. This is the main LSP web inconsistency; the durable value is correct, but the user-facing state is incomplete.
- **The CLI diagnostics toggle has the same pending gap.** `setLspDiagnostics()` only checks `res.ok` and returns `void`, ignoring the 202 body (`/var/www/elowen/src/cli/chat/brainClient.ts:657-667`). The modal then reports unconditional ON/OFF success (`/var/www/elowen/src/cli/chat/pickers.ts:641-653`). A deferred reload should instead say that the setting is saved and activation is pending.
- **Immediate lifecycle toggle errors have no retry affordance.** The web plugin card exposes busy state and error toasts through `usePluginConsent` and `PluginsSection` (`/var/www/elowen/web/modules/settings/usePluginConsent.tsx:71-79`; `/var/www/elowen/web/modules/settings/PluginsSection.tsx:204-211`), but the error path only tells the user that the action failed. The user can repeat the toggle manually, but there is no explicit retry action comparable to `AutoSaveStatus`.
- **The CLI modal also has no retry affordance after a failed toggle/install/uninstall.** `fail()` writes an error notice (`/var/www/elowen/src/cli/chat/pickers.ts:58-63`); recovery requires reopening or repeating the action. This is acceptable for explicit software management, but weaker than the shared autosave contract for the diagnostics toggle.
- **No LSP-specific web regression test exercises the actual manifest field.** Generic tests prove boolean autosave (`/var/www/elowen/web/tests/modules/settings/PluginDetail.test.tsx:199-205`) and the draft's race/error behavior, but the LSP manifest is not used in that path. There is no test proving `diagnosticsEnabled:false` autosaves through the real LSP detail or that a deferred LSP activation is rendered distinctly.

# Legitimate exceptions

- Enabling or disabling the `lsp` plugin is an explicit lifecycle operation: it withdraws or publishes tools/routes and can stop language-server child processes. It should remain an immediate action rather than a debounced form edit. The host applies it through the dedicated plugin toggle route (`/var/www/elowen/src/api/routes/plugins/index.ts:520-538`).
- Installing and uninstalling language servers are explicit software-management actions, not autosave candidates. They affect the host filesystem and executable set; uninstall is destructive and is confirmed in the CLI modal (`/var/www/elowen/src/cli/chat/pickers.ts:621-629`).
- The LSP config contains no secret or per-user field. The manifest declares only `configSchema`, not `userConfigSchema`; the setting is correctly instance-wide and admin-gated.
- The telemetry rail/drawer is intentionally read-only. It reports the plugin control state and must not create a second persistence path.

# Reusable existing pattern

- `usePluginConfigDraft` + `useAutoSaveStatus` is the correct canonical mechanism: 900 ms bounded debounce, serialized full-snapshot writes, stale-draft protection, flush on teardown, invalid-value hold, visible status, and retry (`/var/www/elowen/web/lib/usePluginConfigDraft.ts:52-80,83-112`; `/var/www/elowen/web/lib/useAutoSaveStatus.ts:7-25,45-105`).
- The backend already has the right persistence/activation contract: persistence is the commit point, reload failure/defer is represented as pending rather than as a false save failure (`/var/www/elowen/src/api/routes/plugins/index.ts:116-137,500-518`).
- A structured plugin editor already consumes a pending result for an immediate commit and displays an activation-pending message (`/var/www/elowen/web/modules/settings/PluginConfigEditor.tsx:351-367`; `commitValue` extracts `response.pending` at `:83-101`). That handling should be generalized to ordinary autosave status rather than adding an LSP-specific path.
- The host's generic plugin detail is the single source of truth for schema-driven settings. The LSP plugin should continue to declare only its manifest field and rely on this shared editor (`/var/www/elowen/src/plugins/manifest.ts:12-42,158-164`).

# Tests and gaps

- Existing web coverage proves the generic boolean field reaches the mutation after editing (`/var/www/elowen/web/tests/modules/settings/PluginDetail.test.tsx:199-205`).
- Draft tests cover invalid JSON, secret preservation, immediate commit behavior, pending commit results, and serialized snapshots (`/var/www/elowen/web/tests/modules/settings/usePluginConfigDraft.test.tsx:31-105`).
- Host API tests cover immediate config persistence, deferred activation, post-persistence reload failure, and pre-persistence failure (`/var/www/elowen/tests/api/pluginRoutes.test.ts:339-380`).
- LSP integration tests cover registration, `GET /brain/lsp`, install/uninstall validation, disabled-plugin 503 behavior, lifecycle teardown, and config seeding (`/var/www/elowen-plugins/tests/lspRegistration.test.ts:44-103`; `/var/www/elowen-plugins/tests/lspLifecycle.test.ts:76-171`).
- Missing focused coverage: real LSP manifest → web detail rendering; ordinary autosave receiving `{pending:true}` and exposing an activation-pending state; web toggle error retry; CLI toggle handling of 202; and CLI install/uninstall failure recovery.

# Recommended migration notes

- Extend the shared autosave result/status contract so an accepted save can carry `pending:true`, rendering a distinct “saved; activation pending” state. Do not change LSP into a second custom editor path.
- Make the CLI config client return the parsed pending result for `setLspDiagnostics`; use the existing modal refresh/notice flow to distinguish persisted state from live activation.
- Add a retry affordance to the web plugin lifecycle error state, and a repeatable retry hint for CLI immediate actions. Keep plugin enable/disable, install, and uninstall immediate and explicit.
- Add a focused web regression fixture from the real LSP manifest and a deferred-activation test; add a CLI test asserting that a 202 is not reported as fully active.
- Preserve the current separation: telemetry remains read-only, `/brain/lsp` remains the status API, and `/brain/lsp/install`/`uninstall` remain explicit admin software operations.
