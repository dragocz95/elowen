# Scope

This audit covers the registry `skills` plugin at `/var/www/elowen-plugins/plugins/skills`, including its manifest, browser bundle source, standalone plugin page, settings registration, shared markdown-asset drawer, ownership controls, invocation toggle, delete confirmation, and all plugin-owned persistence routes. Host-side shared primitives, hooks, clients, mutations, routing, and focused tests were inspected where they determine persistence behavior.

The plugin exposes one browser settings section (`skills`) and no separate navigation page. The host resolves the sole section at `/p/skills` and also supports `/p/skills/settings/skills` (`/var/www/elowen/web/app/p/[plugin]/[[...rest]]/page.tsx:95-112`).

# Missing or inconsistent auto-save

- The primary content form is explicit-save only. The shared editor owns `form` locally (`MarkdownAssetEditor.tsx:134-145`), validates it, and persists only from the footer button (`:170-181,388-395`). `SkillsSettings` wires `onSave` to mutations (`SkillsSettings.tsx:166-200`) but never uses the host `useAutoSaveStatus` hook or `AutoSaveStatus` component.
- The host has a save-state channel for plugin settings sections (`/var/www/elowen/web/app/p/[plugin]/[[...rest]]/page.tsx:40-44,111,127-129`), but `SkillsSettings` accepts only `{ surface }` (`SkillsSettings.tsx:18`) and does not report state. Because the plugin declares `ownsPageFrame` and renders its own shell (`index.tsx:11-16`; `SkillsSettings.tsx:205-227`), the host deliberately omits its header and therefore has no fallback place to show save status (`page.tsx:117-143`). A failed save is recoverable only through the toast while the drawer remains open; it is not visibly represented as a persistent saving/error state with retry.
- The immediate invocation toggle is a reasonable bounded mutation, and its optimistic rollback is stronger than the drawer path (`/var/www/elowen/web/lib/mutations.ts:208-227`). It is nevertheless inconsistent with the required canonical feedback: the only failure path is a one-shot toast from `SkillsSettings.tsx:37-41`; no retry or row-local saving state exists.
- Ownership changes are especially fragile for auto-save. `moveSkill` uses the raw runtime API (`SkillsSettings.tsx:46-49`) and is not represented by `saving={create.isPending || update.isPending}` (`:199`). The move and content PATCH are sequential but not transactional (`:177-190`), so auto-saving scope and body together without a transaction or durable draft state could leave the skill moved with old content.
- The form identity is name-only even though the data model explicitly permits the same name for different account owners. The shared editor defines `editing` as `string | null` (`MarkdownAssetEditor.tsx:47-52`), while row identity correctly includes source, owner, and name (`:37-48`). In the plugin, `editedSkill(form)` searches by name alone (`SkillsSettings.tsx:57-67`), so an admin opening duplicate names across owners can resolve the wrong source owner during save/move (`:166-191`). This is a persistence correctness gap that would become more dangerous with background saves.
- Server refresh protection is incomplete. The shared drawer does not overwrite the local draft when query data changes, which preserves typing, but the PATCH API accepts the current body without a server revision precondition (`index.mjs:575-602`). Concurrent edits can therefore lose the newer server state. The API does bump `metadata.version` for content changes (`:597-600`), but that revision is not checked by the client or route.
- Delete is intentionally not auto-save: the confirmation is appropriate, but `confirmDelete` closes the editing drawer immediately after dispatch (`MarkdownAssetEditor.tsx:184-192`). A failed delete therefore loses the open draft context and provides no retry action; this is acceptable only because deletion is a destructive exception, not a model for ordinary edits.

# Legitimate exceptions

- Skill deletion is destructive and irreversible. The existing named confirmation is justified (`MarkdownAssetEditor.tsx:399-406`; daemon DELETE `index.mjs:606-623`). It should remain an explicit confirmed action rather than an auto-save side effect.
- Ownership transfer is a filesystem move that can fail on collisions and may involve moving a directory-form skill with support files (`index.mjs:627-681`). An explicit apply boundary is defensible until move-plus-edit has transactional semantics and clear status handling.
- Bundled skills are shipped read-only and correctly have no persistence surface (`SkillsSettings.tsx:111-125`; `MarkdownAssetEditor.tsx:314-336`).
- Creating a new named skill may retain an explicit first-save boundary if product policy treats the multi-field creation (name, description, markdown body, visibility) as atomic. Subsequent edits should still use the canonical validated auto-save pattern unless this exception is deliberately documented.

# Reusable existing pattern

- `useAutoSaveStatus` is the host's canonical race-safe controller: it debounces validated changes, skips the seed value, serializes in-flight writes, queues the latest state, flushes on close/unmount, and supports retry (`/var/www/elowen/web/lib/useAutoSaveStatus.ts:6-30,45-105`).
- `AutoSaveStatus` renders accessible Saving/Saved/Error + Retry feedback (`/var/www/elowen/web/components/ui/AutoSaveStatus.tsx:7-26`).
- The plugin runtime already exposes both pieces to bundles (`/var/www/elowen/web/lib/pluginUi.tsx:294-305,338-349`), so the skills bundle does not need a new UI primitive or a second save controller.
- Existing host routing can surface a section's reported status in the page masthead (`/var/www/elowen/web/app/p/[plugin]/[[...rest]]/page.tsx:40-44,121-133`). For the frame-owning skills section, the component must render the shared status itself or stop claiming the frame; the host explicitly has no header status in that branch (`:135-143`).
- The existing update mutation's optimistic update, rollback, and settle refetch are reusable for the invocation toggle and can be extended with a visible status channel (`/var/www/elowen/web/lib/mutations.ts:208-227`).

# Tests and gaps

- Shared drawer tests verify row opening, read-only rows, filters, delete reachability, and footer placement, but not auto-save, flush-on-close, retry feedback, or stale server conflict handling (`/var/www/elowen/web/tests/modules/settings/MarkdownAssetEditor.test.tsx:59-172`).
- Host page tests verify that a plugin section can report save state and receive Retry, including the frame-owning channel (`/var/www/elowen/web/tests/app/pluginHostPage.test.tsx:141-209`), but the tests use synthetic sections; there is no focused `SkillsSettings` test proving that the real bundle reports or displays persistence state.
- The skills plugin directory contains no focused test files. Repository searches found no host API test covering the skills CRUD or owner-transfer routes; `pluginRoutes.test.ts` exercises generic plugin management/data routes, not the plugin's skill-file handlers.
- The fake-daemon skills fixture validates that the register has mixed rows and the expected fields (`/var/www/elowen/web/tests/e2e/fake-daemon/handlers/pluginSurfaces.ts:50-62`), but it does not exercise a real create/edit/toggle/move/delete journey.
- Missing regression cases: duplicate skill names across owners; scope move followed by PATCH failure; repeated submit while move is pending; concurrent PATCH/version conflict; close/unmount while a debounce is pending; and visible retry after a failed content save.

# Recommended migration notes

- Make the drawer's draft identity `(name, owner)` rather than name alone, and pass that identity through the shared editor or plugin-specific form state before enabling background writes.
- Use one `useAutoSaveStatus` controller for validated description/body/visibility edits, seeded only after opening an existing row. Flush before drawer close, render `AutoSaveStatus` in the frame-owning drawer footer, and keep the explicit confirmed DELETE separate.
- Decide explicitly whether new-skill creation is an atomic explicit-save exception. If not, create only after the complete draft becomes valid, then autosave later edits with PATCH; do not issue partial invalid files.
- Add a pending/status path for owner transfer and prevent duplicate submits while move-plus-edit is running. Prefer an atomic server operation or a durable compensating strategy before treating scope changes as ordinary background saves.
- Add conditional persistence for content edits (for example, expected metadata version or an equivalent server revision) so a background PATCH cannot silently overwrite a newer server edit. Return a conflict that the drawer can show and let the user retry or reload deliberately.
- Add focused plugin-level UI/API tests for the real save journey and the ownership cases above; retain the existing shared-editor tests as primitive/layout coverage rather than treating them as persistence proof.
